### Authentication
- Share the IP whitelist with each other;
- Bybit Pay signs callbacks using SHA256withRSA (RSA PKCS#1 v1.5 with SHA-256). For details, please see [Signature Algorithm](#signature-algorithm)

### Merchant-specific Webhook RSA Key

A merchant-specific Webhook RSA key is optional. The Key Management page provides two independent key types:

| Key Type | Purpose | How It Is Used |
|:---|:---|:---|
| `RSA_1024_WEBHOOK` | Sign and verify Webhook callbacks | Bybit Pay signs the callback with the private key, and the merchant verifies it with the public key copied from the Merchant Portal. |
| `AES_256` | Encrypt Payout to Card data | The merchant encrypts card data before sending it to Bybit Pay. It is not used for Webhook signing. |

- If `RSA_1024_WEBHOOK` has not been created, callbacks are signed with the Bybit Pay platform key.
- Once `RSA_1024_WEBHOOK` is created, it takes effect immediately and subsequent callbacks are signed with the merchant-specific key.

`RSA_1024_WEBHOOK` uses exactly the same SHA256withRSA algorithm (RSA PKCS#1 v1.5 with SHA-256) as the Bybit Pay platform key. Only the RSA key pair becomes merchant-specific. The signed content, headers, Base64 encoding, and single-line public key format remain unchanged. API request signing is not affected.

#### Create the Key

1. Sign in to the Bybit Pay Merchant Portal.
1. Open [Key Management](https://www.bybit.com/en/bybitpay/psp/dashboard/key-management/).
1. Click **Create new key**.
1. Select `RSA_1024_WEBHOOK`, enter a key name, and confirm the creation.
1. Copy the displayed public key and add it to your webhook verifier.

![Merchant-specific Webhook RSA key in Key Management](/img/bybit-pay-webhook-rsa-key-management.png)

:::danger Creating or deleting this key immediately affects live Webhook verification
Do not create `RSA_1024_WEBHOOK` unless a merchant-specific Webhook key is required and your verifier is ready for the key change. There is no delayed activation. Immediately after creation, new callbacks can no longer be verified with only the Bybit Pay platform public key. If the verifier is not updated in time, Webhook verification will fail and business processing that depends on the notification may be interrupted.

To avoid verification failures during a key change:
- **Create:** Prepare the verifier change before creating the key and perform the operation in a controlled window. Add the new public key immediately after creation and temporarily accept both the platform key and the merchant-specific key.
- **Delete:** Add or retain the platform public key before deletion. Deletion takes effect immediately, so temporarily keep accepting the deleted merchant key for callbacks already in flight.
- **Replace:** Delete the old merchant key, confirm verification with the platform key, then create and add the new merchant key. Accept the applicable old and new keys during each transition.

If uninterrupted Webhook processing is required, the verifier must support multiple public keys during the transition.
:::

### HTTP Request
Method: `POST`<br/> 
URL: provide the callback url in the [Create Payment](create-payment) request parameter `webhookUrl`

### Header
| Parameter | Comments|
|:-----|----- |
|Content-Type |application/json|
|timestamp |Current timestamp (Unix seconds, 10 digits)|
|publicKey |Merchant's RSA public key (optional, used for webhook signature verification)|
|signature |Generated by [Signature Algorithm](#signature-algorithm)|

:::tip Timestamp Format
All timestamp fields in webhook callbacks use **Unix timestamp in seconds** (10 digits):
- Header `timestamp`: `1736236800` (seconds since epoch)
- Body fields (`createTime`, `paymentTime`, `finishTime`): `1736233200` (seconds since epoch)

**Important**: When verifying the signature, use the timestamp values exactly as they appear in the JSON body. Do NOT multiply by 1000.
:::

### Callback Request Parameters
| Parameter | Type | Comments|
|:----- |:-----|----- |
|paymentType |string |Payment type  <li>`E_COMMERCE`: Bybit QR Pay for e-commerce</li><li>`E_COMMERCE_REFUND`: Bybit QR Pay refund for e-commerce</li><li>`ONCHAIN_PAY`: Bybit On-chain pay</li><li>`ONCHAIN_PAY_REFUND`: Bybit On-chain pay refund</li>|

### Signature Algorithm

:::info Signature Method
Bybit Pay webhook uses **JSON body** for signature calculation. The signature string is constructed by concatenating:

**`timestamp` + `JSON_body`**

Where:
- `timestamp`: Current Unix timestamp in seconds (10 digits)
- `JSON_body`: Complete JSON request body as a string (no sorting, no conversion)

**Important**: Do NOT convert the JSON to URL-encoded format. Use the raw JSON string directly.
:::

#### Sign (Bybit Pay Platform)
1. Generate current timestamp (Unix seconds): `timestamp = 1736236800`
2. Marshal the callback data to JSON string (preserve field order as-is)
3. Concatenate: `signContent = timestamp + jsonString`
   ```
   1736236800{"paymentType":"E_COMMERCE","merchantId":"305142568",...}
   ```
4. Encrypt with SHA256 and sign with RSA (PKCS1v15, 1024-bit key)
5. Encode the signature bytes in base64

#### Verify (Merchant Side)
1. Get `timestamp` and `signature` from request headers
2. Read the raw request body as string (do not parse yet)
3. Concatenate: `signContent = timestamp + requestBody`
   ```
   1736236800{"paymentType":"E_COMMERCE","merchantId":"305142568",...}
   ```
4. Decode the signature from base64
5. Verify the signature using SHA256 and Bybit's RSA public key

#### Callback Broker Prefund Order

:::info Broker Prefund Feature
This webhook is triggered for broker prefund orders (payment type: `BROKER_PREFUND`). It notifies merchants about cryptocurrency exchange/conversion order status updates.

**Use Case**: When a merchant processes a fiat-to-crypto or crypto-to-fiat conversion through Bybit's broker service.
:::

```http
POST ${webhook url} HTTP/1.1
Host: www.merchant.com
timestamp: 1736235000
signature: NgDZLZCVBdma904hzZXmU+fQ7dr7z7muZkuwAbDnibLXXXXXXXXXXXXgmzad58Lf...
Content-Type: application/json

{
    "tradeNo": "DL202601280001",
    "status": "completed",
    "quoteTxId": "QUOTE-20260128-001",
    "exchangeRate": "1.0025",
    "fromCoin": "USD",
    "fromCoinType": "fiat",
    "toCoin": "USDT",
    "toCoinType": "crypto",
    "fromAmount": "1000.00",
    "toAmount": "998.75",
    "createdAt": "1736235000000",
    "subUserid": "12345678"
}
```

**Broker Prefund Order Fields:**

| Field | Type | Description |
|:------|:-----|:------------|
| tradeNo | string | Broker deal order ID |
| status | string | Order status: `pending`, `completed`, `failed`, `cancelled` |
| quoteTxId | string | Quote transaction ID (price lock ID) |
| exchangeRate | string | Exchange rate applied (unit price) |
| fromCoin | string | Source currency/coin |
| fromCoinType | string | Source currency type: `fiat` or `crypto` |
| toCoin | string | Destination currency/coin |
| toCoinType | string | Destination currency type: `fiat` or `crypto` |
| fromAmount | string | Source amount (how much user pays) |
| toAmount | string | Destination amount (how much user receives) |
| createdAt | string | Order creation timestamp in **milliseconds** (13 digits) |
| subUserid | string | Sub-user ID (slave UID) |

**Status Values:**
- `pending`: Order is being processed
- `completed`: Order completed successfully
- `failed`: Order failed
- `cancelled`: Order was cancelled

**Note**: Unlike payment orders, the `createdAt` field in broker prefund orders uses **milliseconds** (13 digits), not seconds.

### Auth

Auth reuses the existing Payment Notify webhook. The webhook URL, method, authentication, signature, headers, response, and retry rules remain unchanged.
The existing `PayOrder` webhook body adds the following fields:

| Field Name | Type | Required | Description |
| --- | --- | --- | --- |
| `authStatus` | string | Yes | Current authorization status: `SUCCESS`, `REJECTED`, `OVERTIME`, or `EXPIRED`. |
| `authExpireAt` | string | No | Authorization expiry time as a UTC Unix timestamp in milliseconds. Returned for `SUCCESS`. |
| `customer` | [`Customer Type`](data-model/customer) | No | Authorized customer fields. Returned only for `SUCCESS` while the authorization remains valid. |

The webhook is triggered after authorization reaches `SUCCESS`, `REJECTED`, or `OVERTIME`. `PENDING` does not trigger a merchant webhook. Authorization expiry itself does not trigger an additional webhook; query `/v5/bybitpay/pay_result` for the current status. If delivery or retry of an existing success notification occurs after the authorization has expired, the notification reflects the current `EXPIRED` status and does not include `customer`.
